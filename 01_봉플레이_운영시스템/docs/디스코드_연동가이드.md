# 봉플레이 운영시스템 — 디스코드 경보 연동 가이드

사고·민원·마감·설비 이벤트를 디스코드 채널로 **자동 통보**하는 설정입니다.
**최초 1회만 하면 되고, 약 15분 걸립니다.**

파일: **`supabase_discord_setup.sql`** ← 이 파일을 Supabase SQL Editor 에 붙여넣습니다.

---

## 왜 프론트엔드가 아니라 Supabase에 넣는가

이 시스템은 **입력이 항상 기기에 먼저 저장**되고, 네트워크가 복구되면 클라우드로 올라갑니다.
만약 화면(브라우저)에서 디스코드로 알림을 보내면:

| 문제 | 결과 |
|---|---|
| 오프라인 동안 알림 발송 | **사고 알림이 그냥 증발** |
| 복구 시 대기열 일괄 업로드 | 같은 알림이 **수십 건 중복 도착** |
| 웹훅 URL이 브라우저에 노출 | 누구나 **가짜 경보를 위조** 가능 |

그래서 알림은 **DB가** 쏩니다. 화면이 꺼져 있어도, 현장 기기가 오프라인이어도,
데이터가 클라우드에 도착하는 순간 알림이 나갑니다.

---

## 0단계 — 준비물 확인

디스코드에서 만든 웹훅 URL **4개**가 필요합니다. 없으면 먼저 발급하십시오.
채널 → 톱니바퀴 → **연동 → 웹훅 → 새 웹훅 → URL 복사**

| 필요한 채널 | `channel_key` (정확히 이 철자) | 받는 알림 |
|---|---|---|
| 🚨 비상·사고경보 | `emergency` | 119 출동, 중대/보통 사고 접수 |
| ⚠️ 민원·리스크 | `complaint` | 중대민원 접수, **누적 2건째 계약 리스크** |
| 📊 일일·운영마감 | `daily` | 개장 브리핑(09:00), 마감 정산 |
| 🔧 설비·안전일지 | `facility` | 안전점검 미실시, 설비 수명, 기상 임계, 준사고 일지 |

> ⚠ **`channel_key` 는 위 철자를 그대로** 써야 합니다. 오타가 나면 알림이 전송되지 않고
> 큐에만 쌓입니다. 이게 가장 흔한 실수입니다.

---

## 1단계 — 확장 기능 켜기

Supabase 좌측 메뉴 → **Database → Extensions** 에서 두 개를 검색해 **켜기**:

- `pg_net` — 디스코드로 HTTP 전송
- `pg_cron` — 정해진 시각에 브리핑 발송

> `pg_cron` 이 없으면 **즉시 발생형**(사고·민원·마감·기상)은 정상 동작하고,
> **정기형**(아침 브리핑, 안전점검 미실시, 설비 점검, 준사고 일지)만 동작하지 않습니다.

---

## 2단계 — 스크립트 실행 (1차: 구조 생성)

1. Supabase 좌측 메뉴 → **SQL Editor** → **New query**
2. `supabase_discord_setup.sql` **파일 내용 전체**를 복사해 붙여넣기
3. 우측 하단 **Run**
4. `Success. No rows returned` 또는 마지막 `select` 결과가 나오면 성공

이 단계에서는 웹훅 URL 을 아직 넣지 않아도 됩니다. URL 등록 부분은 주석 처리되어 있습니다.

> 실행 중 **경고(warning)** 가 보여도 정상일 수 있습니다.
> `예약 작업 등록 실패(...)` 경고는 `pg_cron` 이 꺼져 있다는 뜻이며,
> 1단계를 켠 뒤 **7절만 다시 실행**하면 해결됩니다.

---

## 3단계 — 웹훅 URL 등록

SQL Editor 에 **새 쿼리**를 열고 아래를 붙여넣습니다.
`여기에_..._URL` **4곳만** 실제 주소로 바꾸십시오.

```sql
insert into public.ops_discord_webhooks (channel_key, webhook_url, label, username) values
  ('emergency', '여기에_비상_사고경보_URL', '🚨 비상·사고경보', '봉플레이 비상관제봇'),
  ('complaint', '여기에_민원_리스크_URL',   '⚠️ 민원·리스크',    '봉플레이 민원관제봇'),
  ('daily',     '여기에_일일_운영마감_URL', '📊 일일·운영마감',  '봉플레이 운영봇'),
  ('facility',  '여기에_설비_안전일지_URL', '🔧 설비·안전일지',  '봉플레이 설비봇')
on conflict (channel_key) do update
  set webhook_url = excluded.webhook_url,
      label       = excluded.label,
      username    = excluded.username,
      updated_at  = now();
```

**Run** → `Success. No rows returned` 확인.

> URL 을 나중에 바꾸고 싶으면 **위 명령을 다시 실행**하면 됩니다 (덮어쓰기).

## 4단계 — 정상 동작 확인

SQL Editor 에서 한 줄씩 실행해 결과를 눈으로 확인하십시오.

**① 웹훅 4개가 등록됐는가**

```sql
select channel_key, label, enabled, left(webhook_url, 45) || '...' as url_head
  from public.ops_discord_webhooks order by channel_key;
```

→ 4행이 나와야 합니다. `enabled` 가 모두 `true` 인지 확인.

**② 예약 작업이 걸렸는가**

```sql
select jobname, schedule, active from cron.job order by jobname;
```

→ `bongplay_` 로 시작하는 6개가 나와야 합니다.

**③ 파이프라인 전체 테스트 (실제로 디스코드에 도착하는지)**

```sql
select public.ops_discord_enqueue(
  'emergency', 'manual_test', 'test-' || to_char(now(),'YYYYMMDDHH24MISS'), 'v1',
  public.ops_embed('🧪 연동 테스트', 6583435,
    jsonb_build_array(jsonb_build_object('name','상태','value','정상 연동 확인','inline',true))),
  1);

select public.ops_discord_flush();
```

→ `비상·사고경보` 채널에 카드가 **즉시** 도착하면 성공입니다.
도착하지 않으면 아래 [문제 해결](#문제-해결) 로 이동하십시오.

**④ 발송 상태 요약**

```sql
select * from public.ops_discord_health;
```

| 컬럼 | 읽는 법 |
|---|---|
| `queued` | 대기 중. 계속 늘어나면 **웹훅 등록/철자 문제** |
| `sent` | 정상 발송 |
| `dead` | 영구 실패. `error` 값이 `HTTP 404` 면 웹훅이 삭제된 것 |

## 어떤 일이 생기면 어떤 알림이 오나

| 원천 화면 / 동작 | 저장 위치 | 채널 | 시점 |
|---|---|---|---|
| 사고 발생 입력 (중대·보통) | `incident_logs` | 🚨 emergency | 즉시 |
| 119 출동 체크 | `incident_logs` | 🚨 emergency | 즉시 (최우선 순위) |
| 준사고·경미사고 | `incident_logs` | 🔧 facility | 매일 18:00 묶음 1건 |
| 중대민원 접수 | `complaint_logs` | ⚠️ complaint | 즉시 |
| **중대민원 2건째** | `complaint_logs` | ⚠️ complaint | 즉시 (계약 리스크 경보) |
| 마감 정산 입력 | `closing_records` | 📊 daily | 즉시 |
| 개장 브리핑 | (자동 집계) | 📊 daily | 매일 09:00 |
| 안전점검 미실시 | `safety_audits` | 🔧 facility | 매일 09:40 |
| 설비 수명 90% / 점검 공백 | `asset_usage_counters` | 🔧 facility | 매일 08:30 |
| 강풍 12m/s · 폭우 | `weather_environment_telemetry` | 🔧 facility | 즉시 (1시간 1건) |

브리핑에는 **어제 매출·BEP 달성률(기준 66만원)**, **오늘 단체예약**, **오늘 기상**, **평일/주말 목표**가 들어갑니다.

## 개인정보 — 반드시 지켜지는 구조입니다

이 시스템은 보호자 성명·연락처·자녀 정보·서명을 수집합니다.
**이 값들은 디스코드로 전송되지 않습니다.** 코드가 그렇게 막아두었습니다.

| 데이터 | 전송 여부 |
|---|---|
| 사고 `person_name` / `person_phone` | ❌ 전송 안 함 (구조적 차단) |
| 민원 `person_name` / `person_phone` | ❌ 전송 안 함 (구조적 차단) |
| `safety_consents` (동의서·서명) | ❌ 연동 자체가 없음 |
| 사고 경위·조치 자유서술 | ❌ **기본 전송 안 함** |
| 기록 ID / 심각도 / 시각 / 시설 / 장소 | ✅ 전송 (응급 대응에 필요한 최소 정보) |

자유서술까지 받고 싶으면 아래를 실행할 수 있습니다. 이 경우에도 **연락처·식별번호·보호자 이름은
정규식으로 마스킹된 뒤** 전송됩니다.

```sql
update public.ops_discord_webhooks
   set include_free_text = true
 where channel_key = 'emergency';
```

> ⚠ 그래도 **디스코드는 해외 사업자**입니다. 마스킹이 완벽하지 않을 수 있으므로,
> 자유서술 전송은 기본값(미포함)으로 두는 편이 안전합니다.

## 조정할 수 있는 값

| 바꾸고 싶은 것 | 방법 |
|---|---|
| 중대민원 임계 (기본 2건) | SQL 파일의 `v_threshold int := 2;` 수정 후 해당 함수만 재실행 |
| 중대민원 조회 기간 (기본 90일) | 같은 함수의 `v_window int := 90;` |
| 비상 채널 강제 호출(@here) | `update public.ops_discord_webhooks set mention='@here' where channel_key='emergency';` |
| 브리핑 시각 | `select public.ops_schedule_job('bongplay_daily_briefing','0 0 * * *', $$select public.ops_daily_briefing();$$);` 에서 첫 인자가 **UTC** (00:00 UTC = 09:00 KST) |
| 채널 일시 중단 | `update public.ops_discord_webhooks set enabled=false where channel_key='daily';` |
| 특정 알림 끄기 | `drop trigger trg_weather_discord on public.weather_environment_telemetry;` |

> ⚠ `@here` 는 사람을 실제로 울립니다. 비상 채널에만, 정말 필요할 때만 켜십시오.
> 켜지 않아도 디스코드 앱에서 **채널 알림을 "모든 메시지"로 설정**하면 알림은 옵니다.

## 문제 해결

| 증상 | 원인 / 조치 |
|---|---|
| 테스트 메시지가 안 옴. `queued` 만 계속 쌓임 | `channel_key` 철자 오류 또는 웹훅 미등록. ① 쿼리로 4행 확인 |
| `dead` 가 늘어남, `error` 가 `HTTP 404` | 채널 웹훅이 삭제됨 → 웹훅 재발급 후 **3단계** 재실행 |
| `dead`, `error` 가 `HTTP 401/403` | URL 복사가 잘못됨(앞뒤 공백·중간 누락). 다시 복사 |
| `HTTP 429` 가 계속 | 잠시 기다리면 자동 재시도. 지속되면 채널별 상한을 `6` → `3` 으로 낮춤 |
| 브리핑·점검이 안 옴 | `pg_cron` 미활성. 1단계 후 **7절 재실행**. ② 로 `cron.job` 확인 |
| 알림이 너무 많이 옴 | 경보가 아니라 **묶음(다이제스트)** 성격인 것을 `enabled=false` 로 끔. 채널을 나눈 이유가 이것 |
| 오프라인 중 사고가 나서 알림이 늦게 옴 | 정상 동작입니다. 제목에 **`⏱ 지연 접수`** 가 붙어 도착합니다 |
| 예전 기록이 계속 쌓임 | 월 1회 아래 실행 |

```sql
delete from public.ops_discord_queue
 where status in ('sent','dead','skipped')
   and created_at < now() - interval '90 days';
```

## 웹훅 URL 이 유출됐다면

웹훅 URL 은 **비밀번호와 같습니다.** 노출되면 아무나 이 채널로 가짜 경보를 쏠 수 있습니다.

1. 디스코드 채널 → 톱니바퀴 → 연동 → 웹훅 → **기존 웹훅 삭제**
2. **새 웹훅 만들기** → 새 URL 복사
3. **3단계**의 `insert ... on conflict do update` 명령을 새 URL 로 재실행

> `config.js` 나 깃허브, 단톡방에는 **절대** 넣지 마십시오.
> URL 은 DB 안에만 있고, 브라우저로는 내려가지 않습니다.

## 알려진 한계 (미리 알고 계셔야 할 것)

1. **최대 60초 지연** — 발송 엔진이 1분마다 돌기 때문입니다. 119 급 긴급은
   디스코드 알림과 **별개로 전화 연락망**을 함께 쓰십시오.
2. **정기형 알림은 `pg_cron` 에 의존** — 꺼져 있으면 즉시형만 동작합니다.
3. **디스코드 웹훅은 단방향**입니다. `/마감` 같은 **명령으로 입력하는 기능은 없습니다**
   (그건 별도 봇 개발이 필요합니다).
4. **양방향 봇·다이제스트 고도화는 아직 미구현** — 현재는 위 표의 범위까지입니다.
5. 이 SQL 은 **실제 Postgres 서버에서 실행 검증되지 않았습니다.**
   반드시 **4단계 확인 쿼리**로 하나씩 점검한 뒤 운영에 투입하십시오.
   특히 ③ 파이프라인 테스트는 운영 투입 전 필수입니다.
