## 0. 개정 이력

- v1: 요약본만 보고 작성. "JEV·RLCD는 확인 불가", "강화학습이라는 표현은 과장 가능성"이라고 적었다.
- **v2 (현재): 틀린 판단을 정정했다.** Jev는 TypeSafe AI가 2026년 9월에 공개한 실제 모델이고, RLCD
  (Reinforcement Learning for Calibrated Decisions)는 그 회사가 밝힌 실제 학습 방식이다. RL이라는 용어는
  **학습 단계** 를 가리키는 것으로 정당하다. 아래 1절을 이에 맞춰 다시 썼다.

## 1. Jev는 무엇인가 (확인된 사실)

| 항목 | 내용 |
|---|---|
| 개발사 | TypeSafe AI (투자 약 4,000만 달러로 보도) |
| 분류 | "System One 모델" — 사람이 읽을 글이 아니라 **소프트웨어가 바로 쓸 판단** 을 내는 모델 |
| 입력 | **state**(텍스트 또는 JSON) + **questions**(여러 개) |
| 질문 유형 | **Choice**(선택지 중 하나), **Score**(점수), **Noul**(예/아니오 확률) |
| 출력 | 타입이 정해진 값 + **보정된(calibrated) 확률** + 신뢰도. 자유 텍스트는 내지 않는다 |
| 처리 | 여러 질문을 **한 번의 호출에서 병렬로** 답한다 (자기회귀 생성이 아닌 병렬 샘플러) |
| 학습 | **RLCD** — 사람 선호(RLHF)나 검증 가능한 정답(RLVR)이 아니라 "확률이 정직한가"를 보상으로 삼는 강화학습 |
| 지연 | 회사 발표 기준 호출당 약 70~500ms. 둠(Doom) 시연에서 판단당 0.114초 |
| 가격 | 입력 100만 토큰당 0.042달러, 출력 무료 (발표 기준) |
| 형태 | 호스팅 API (LiteLLM 패스스루 지원) |

**요약본의 설명 중 맞는 것:** 생성 대신 선택, 병렬 판단, 확률 기반 사람 승인 구간.
**요약본에서 주의할 것:** 영상 실습(Qwen 로컬 모델로 비교)은 원리 시연이고, Jev 자체의 성능 측정이 아니다.
"환각이 없다"는 문구는 **지어낸 문장을 출력할 수 없다** 는 뜻이지, **틀린 선택지를 고를 수 없다** 는 뜻이 아니다.

### InstructGPT 논문과의 관계 — 같은 "강화학습", 다른 목표

| | RLHF (InstructGPT) | RLCD (Jev) |
|---|---|---|
| 보상 기준 | 사람 평가자의 **선호 순위** | 예측 확률의 **정직함(보정)** |
| 결과물 | 사람이 좋아하는 **글** | 코드가 믿을 수 있는 **판단 + 확률** |
| 논문·발표의 핵심 수치 | 1.3B 모델이 175B GPT-3보다 선호됨. 175B 기준 선호율 85±3%. 폐쇄형 과제 환각률 21% (GPT-3 41%) | 판단당 0.1초대, LLM 대비 약 100배 빠름 (회사 주장) |

InstructGPT 논문에서 우리에게 남는 교훈은 세 가지다.

1. **작고 잘 맞춘 모델이 크고 안 맞춘 모델을 이긴다.** 문의·리뷰 같은 대량 작업에 Haiku를 쓰는 현재 선택과 같은 방향이다.
2. **정렬해도 환각은 줄 뿐 사라지지 않는다** (21%). 요금·안전처럼 틀리면 안 되는 정보는 모델 생성에 맡기지 않는 현재 원칙이 맞다.
3. **"누구의 선호인가"가 결과를 정한다.** 논문은 평가자 약 40명의 선호를 학습했다고 스스로 한계로 적는다.
   우리에게는 **현장 직원이 초안을 고친 기록** 이 그 "선호 데이터"다. 모델을 학습시키지는 않더라도,
   이 기록을 모으면 프롬프트 개선과 평가셋 구축에 바로 쓸 수 있다.

## 2. 현재 에이전트 진단 — 이미 "선택" 구조가 상당 부분 들어와 있다

봉뜨락 에이전트의 설계 원칙은 README에 명시돼 있다: **"계약 준수가 걸린 계산을 모델 판단에 맡기지 않는다."**
판단 가능한 것은 **결정론적 규칙(파이썬)** 으로, 판단이 위험한 것은 **사람** 에게 보낸다.

| 에이전트 | 판단 방식 | Jev 관점에서 본 상태 |
|---|---|---|
| `faq_agent` 이관 여부 | 키워드 규칙 (API 0회) | 결정론적. Jev보다 강한 보장 |
| `faq_agent` 답변 | Haiku, `can_answer`(bool) + 답변 문장을 **한 번에 생성** | 판단과 생성이 섞여 있음 → **개선 여지** |
| `review_agent` 분류 | Haiku, `sentiment`·`category` 를 **자유 문자열(str)** 로 받음 | 선택지를 프롬프트로만 강제 → **개선 여지** (Jev의 Choice와 정확히 맞는 과제) |
| `review_agent` 차단 | 키워드 규칙 | 결정론적 |
| `safety`·`complaint`·`admin`·`cashflow` | 기한·상태·집계는 파이썬, AI는 문서 초안만 | "판단 레이어"가 이미 코드로 존재 |
| `forecast`·`daily_report` | 수치는 파이썬, AI는 브리핑 문장만 | 동일 |
| `content`·`sales`·`emergency` | 생성이 본업 | Jev 대상 아님 (Jev는 글을 쓰지 못함) |

**Jev가 풀려는 핵심 문제(에이전트 간 자연어 통신의 비용·지연)는 현재 구조에 없다.** 11종은 사람이 CLI로 부르는
독립 도구이고, 에이전트끼리 대화하는 오케스트레이션 레이어가 없다.

## 3. 비용·속도 관점의 현실 점검

- README 추정 월 API 비용: **약 15,000원**. 분류 호출을 Jev로 옮겨 거의 0원이 돼도 절감액은 월 수천 원이다.
- 문의 응답은 Haiku 단건 호출이라 현장 체감 병목이 아니다.

→ 지금 Jev를 쓸 이유는 비용이 아니라 **보정된 확률** 이다. Claude API는 토큰 확률을 제공하지 않으므로,
"확률이 애매하면 사람에게" 같은 설계는 Claude만으로는 만들 수 없다. **Jev가 이 빈칸을 채울 수 있다.**

## 4. 적용할 가치가 있는 곳 (우선순위순)

### ① `faq_agent` — 의도 "선택" 후 답은 설정값에서 꺼내기 ★ 모델과 무관하게 가장 효과 큼
```
1단계  키워드 이관 (현행 유지, 결정론)
2단계  의도 선택: [요금, 운영시간, 위치·주차, 예약, 연령·키 기준, 단체, 기타, 사람필요]
       - Claude: 구조화 출력 enum
       - Jev:    Choice 질문 + 확률 → 최고 확률이 낮으면 '사람필요'로
3단계  요금·운영시간·위치 → config.py 값을 템플릿에 채워 응답 (생성 0)
       기타 → 지금처럼 Haiku가 답 생성
```
효과: 요금이 바뀌어도 **모델이 숫자를 틀릴 경로 자체가 사라진다.**

### ② `review_agent` — 자유 문자열을 선택지로
- Claude 유지 시: `sentiment`·`category` 를 `Literal[...]` enum으로 (수 줄 수정).
- Jev 사용 시: Choice 2개 + Noul 1개(`actionable`)를 한 호출로. 확률이 낮은 리뷰만 사람이 확인.

### ③ 확률 기반 사람 승인 — Jev의 진짜 가치
리뷰 분류, 문의 의도, 향후 통합 창구 라우팅처럼 **틀려도 되돌릴 수 있는 판단** 에만 확률 임계값을 쓴다.
예: 최고 확률 0.8 이상 자동 처리, 미만은 사람 확인 대기열.
**안전·사고·분쟁 이관은 확률에 맡기지 않는다.** 키워드 게이트가 항상 먼저 돈다.

### ④ 통합 창구가 생길 때 — 병렬 라우터
"환불해 주세요, 아이가 네트에서 다칠 뻔했어요" → 안전(사람) + 민원(3일 기한) + 환불(분쟁).
Jev의 "여러 질문을 한 호출에서 병렬로"가 정확히 이 구조다. 단, 키워드 게이트가 1순위.

## 5. Jev 도입 전 확인할 것

| 항목 | 이유 |
|---|---|
| **한국어 성능** | 확인된 자료가 없다. 짧은 구어체 문의·리뷰에서 직접 측정해야 한다 |
| **보정의 실제 품질** | "확률이 정직하다"는 회사 주장이다. 우리 데이터로 0.8이라고 한 것 중 실제로 80%가 맞는지 확인 |
| **개인정보** | 문의·리뷰에는 이름·연락처가 섞인다. 새 외부 업체로 보내기 전 약관·보관 정책 확인, 필요하면 마스킹 |
| **업체 지속성** | 2026년 9월 공개된 신생 서비스다. 운영 핵심 경로에 넣기 전에 대체 경로(Claude enum)를 남겨둔다 |
| **평가셋** | 비교하려면 정답이 달린 실제 문의·리뷰 50~100건이 필요하다. 개장 전에는 없으므로 11월 이후 |

### 권장 실험 (소프트 오픈 이후)
1. 실제 리뷰·문의 100건에 사람이 정답 라벨을 단다.
2. 같은 100건을 (a) Haiku + enum, (b) Jev Choice로 분류한다.
3. 정확도, 지연, 비용, **확률 구간별 실제 정답률(보정 곡선)** 을 비교한다.
4. Jev가 보정에서 확실히 낫다면 ②·③부터 옮긴다.

## 6. 리플레이스(RE:PLAYCE) 관점의 시사점

> **결정은 규칙과 선택으로, 생성은 사람이 검토할 문서에만.**

지자체 고객에게는 속도보다 **설명 가능성** 이 중요하다(감사·의회 대응). "이 민원이 왜 3일 기한 대상인가"에
규칙과 선택지, 그리고 확률로 답할 수 있는 구조는 B2G 신뢰에 유리하다. 지원서의 "운영 인텔리전스 플랫폼"은
이 구조 위에 설명하는 편이 좋다. Jev 같은 판단 전용 모델은 그 판단 레이어를 구현하는 선택지 중 하나이고,
의존하지 않고도 같은 원칙을 지킬 수 있도록 설계해 두는 것이 안전하다.

## 7. 제안 (구현은 별도 승인 후)

| 순위 | 작업 | 규모 | 기대 효과 |
|---|---|---|---|
| 1 | `review_agent` 의 `sentiment`·`category` 를 enum으로 | 수 줄 | 집계 오염 방지 |
| 2 | `faq_agent` 를 "의도 선택 → 설정값 템플릿 응답" 2단계로 | 소 | 요금·시간 환각 차단 |
| 3 | 직원이 고친 초안·이관 결과를 기록하는 피드백 로그 | 소 | 평가셋·프롬프트 개선의 원천 (InstructGPT 교훈 3) |
| 4 | 소프트 오픈 후 Haiku enum vs Jev 비교 실험 | 소 | 확률 기반 사람 승인 도입 여부 결정 |
| 5 | 통합 창구 도입 시 병렬 라우터 | 중 | 다중 처리, 누락 방지 |
