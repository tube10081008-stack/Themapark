## 1. 요약본 검증 — 무엇이 단단하고 무엇이 불확실한가

| 요약본 주장 | 판단 | 근거 |
|---|---|---|
| 에이전트끼리 자연어로 주고받으면 느리고 비싸다 | **맞음** | 출력 토큰은 입력보다 비싸고 느리다. 판단 결과를 문장으로 생성할 이유가 없다 |
| 판단은 "생성" 대신 후보 중 "선택"으로 하면 빠르고 정확하다 | **맞음 (핵심)** | 후보 라벨의 점수를 비교하는 분류는 오래된 기법이다. 출력이 짧고, 형식 오류가 없다 |
| 이것이 "강화학습(RL)"이다, Q(S,A) 정책이다 | **과장 가능성** | 추론 시점에 후보 점수를 매기는 것은 RL이 아니다. RL은 보상으로 정책을 **학습**시킬 때의 이야기다. 용어를 빌려 쓴 것으로 보인다 |
| "JEV", "RLCD" | **확인 불가** | 공개 표준 용어로 확인하지 못했다. 요약본 자체가 AI 생성물이라 용어가 변형됐을 수 있다. 원 영상에서 정확한 명칭·논문을 확인할 것 |
| 속도 50% 이상 향상 | **조건부** | 비교 대상이 "JSON 문장 생성"이다. 이미 짧은 enum 출력을 쓰는 구조와 비교하면 차이는 훨씬 작다 |
| 확률 0.5 근처면 사람 승인 | **개념은 맞음** | 다만 아래 3절 참고 — Claude API에서는 이 확률을 그대로 얻을 수 없다 |

**Claude API와의 차이 (중요):** 영상의 실습은 로컬 모델(Qwen 2.5)에서 **토큰 확률(logprob)** 을 직접 읽는
방식이다. 우리가 쓰는 Claude Messages API는 토큰 확률을 제공하지 않는다(API 문서 기준). 따라서 영상 기법을
그대로 옮길 수는 없고, 같은 효과는 **구조화 출력 + enum(선택지 고정)** 으로 얻는다.

## 2. 현재 에이전트 진단 — 이미 "선택" 구조가 상당 부분 들어와 있다

봉뜨락 에이전트의 설계 원칙은 README에 명시돼 있다: **"계약 준수가 걸린 계산을 모델 판단에 맡기지 않는다."**
이 원칙은 영상의 주장보다 한 단계 더 나간 것이다. 판단을 확률적 선택으로 바꾸는 게 아니라, 판단 가능한 것은
**결정론적 규칙(파이썬)** 으로, 판단이 위험한 것은 **사람** 에게 보낸다.

| 에이전트 | 판단 방식 | 영상 관점에서 본 상태 |
|---|---|---|
| `faq_agent` 이관 여부 | 키워드 규칙 (API 0회) | 이미 "선택"보다 강함 — 결정론적 |
| `faq_agent` 답변 | Haiku, `can_answer`(bool) + 답변 문장을 **한 번에 생성** | 판단과 생성이 한 호출에 섞여 있음 → **개선 여지** |
| `review_agent` 분류 | Haiku, `sentiment`·`category` 를 **자유 문자열(str)** 로 받음 | 선택지를 프롬프트로만 강제 → **개선 여지** |
| `review_agent` 차단 | 키워드 규칙 | 결정론적 |
| `safety_agent`, `complaint_agent`, `admin_agent`, `cashflow_agent` | 기한·상태·집계 모두 파이썬, AI는 문서 초안만 | 영상이 말하는 "판단 레이어"가 이미 코드로 존재 |
| `forecast_agent`, `daily_report` | 수치는 파이썬, AI는 브리핑 문장만 | 동일 |
| `content_agent`, `sales_agent`, `emergency_agent` | 생성이 본업 | 선택으로 바꿀 대상 아님 |

**영상의 핵심 문제(에이전트 간 자연어 통신 비용)는 우리 구조에 없다.** 11종은 사람이 CLI로 부르는 독립
도구이고, 에이전트끼리 대화하는 오케스트레이션 레이어가 없다.

## 3. 비용·속도 관점의 현실 점검

- README 추정 월 API 비용: **약 15,000원** (마케팅 20건 + 문의 800건 + 제안서 15건).
- 분류 호출(문의·리뷰)을 모두 절반으로 줄여도 절감액은 **월 수천 원** 수준이다.
- 문의 응답 속도도 Haiku 단건 호출이라 현장 체감 병목이 아니다.

→ **"속도·비용" 목적의 도입은 투자 대비 효과가 거의 없다.** 이 아이디어를 쓸 이유는 속도가 아니라
**정확성과 통제 가능성** 이다. 아래 4절은 전부 그 관점이다.

## 4. 적용할 가치가 있는 곳 (우선순위순)

### ① `faq_agent` — 의도 "선택" 후 답은 설정값에서 꺼내기 ★ 가장 효과 큼
현재는 모델이 요금·운영시간이 담긴 프롬프트를 읽고 **답 문장을 생성** 한다. 요금 같은 사실 정보는 생성할
필요가 없다.

```
1단계  키워드 이관 (현행 유지, 결정론)
2단계  의도 선택: enum = [요금, 운영시간, 위치·주차, 예약, 연령·키 기준, 단체, 기타, 사람필요]
3단계  요금·운영시간·위치 등 → config.py 값을 템플릿에 그대로 채워 응답 (생성 0)
       기타 → 지금처럼 Haiku가 답 생성
```

효과: 요금이 확정·변경돼도 **모델이 숫자를 틀릴 경로 자체가 사라진다.** 영상의 "생성→선택"이 여기서는
속도가 아니라 **환각 차단** 으로 작동한다.

### ② `review_agent` — 자유 문자열을 enum으로
`sentiment: str`, `category: str` 을 `Literal[...]` 로 바꾸면 구조화 출력이 선택지 밖 값을 원천 차단한다.
지금은 모델이 "부정적" 같은 변형을 내면 `stats` 집계가 조용히 갈라진다. 작은 수정, 확실한 효과.

### ③ 향후 통합 창구(카카오 채널 등)가 생길 때 — 다중 라벨 라우터
하나의 메시지에 여러 처리가 필요한 경우가 있다.
예: "환불해 주세요, 아이가 네트에서 다칠 뻔했어요" → 안전(사람) + 민원(3일 기한) + 환불(분쟁).
이때 **다중 선택 enum 한 번** 으로 필요한 도구를 동시에 트리거하는 것이 영상의 "병렬 호출" 과 같은 구조다.
단, **안전 키워드 게이트가 항상 먼저** 다. 라우터는 그 뒤에서 나머지를 나눈다.

### ④ 사람 승인 구간 — 확률 대신 "모름" 선택지
Claude API에서는 토큰 확률을 얻을 수 없고, 모델에게 "확신도 0~1"을 **말하게** 하는 것은 신뢰하기 어렵다.
대신 enum에 **`사람필요` / `판단불가` 선택지를 명시** 하는 방식(현재 `can_answer=False` 와 같은 발상)이
안전하다. 안전·분쟁 판단을 확률 임계값에 맡기는 설계는 **채택하지 않는다.**

### ⑤ 로컬 모델(Qwen) 스코어링 — 지금은 비권장
서버·GPU 운영 부담, 한국어 분류 품질 검증 비용, 고객 문의 데이터의 외부 반출·보관 문제가 생긴다.
문의량이 하루 수천 건 이상으로 커지고 분류 비용이 실제 병목이 될 때 재검토한다.

## 5. 지켜야 할 선

- 안전·사고·분쟁 이관은 **키워드 게이트(결정론)가 1순위** 로 남는다. 어떤 분류기도 이 앞에 두지 않는다.
- 분류 방식을 바꾸면 `test_escalation.py`(21건)·`test_tier3.py`(리뷰 차단 포함)를 반드시 다시 돌린다.
- 의도 분류를 도입하면 **오분류 사례 평가셋** (실제 문의 50~100건)을 먼저 만든다. 개장 전에는 실데이터가
  없으므로, 11월 소프트 오픈 이후 쌓이는 문의로 만드는 것이 현실적이다.

## 6. 리플레이스(RE:PLAYCE) 관점의 시사점

지원서가 내세운 "운영 인텔리전스 플랫폼"에 이 분석은 좋은 원칙 한 줄을 준다.

> **결정은 규칙과 선택으로, 생성은 사람이 검토할 문서에만.**

지자체 고객에게 중요한 것은 속도보다 **설명 가능성** 이다(감사·의회 대응). "이 민원이 왜 3일 기한 대상으로
분류됐는가"에 규칙과 선택지로 답할 수 있는 구조는, LLM이 자유롭게 판단하는 구조보다 B2G에서 신뢰를 얻기 쉽다.
봉뜨락 에이전트가 이미 그 방향으로 설계돼 있다는 점은 지원서의 차별점으로 쓸 수 있다.
