## 목표

현행 업무로그와 과거 구현의 차이, 실제 배포본과 시트 연결 상태를 증거로 확인한다. 벤이 이관·수정 작업을 배정할 수 있도록 기능별 비교표와 재현 가능한 문제 목록을 제출한다. API 접근이 없어도 로그인된 GitHub·Netlify·Google Sheets 화면을 이용해 진행한다.

3. 실제 기준 SHA와 착수 상태를 작업표의 GEO-001 행에 기록한다. 현재 접속 가능한 사이트, 저장소 읽기/쓰기, 별도 테스트 환경 유무를 확인한다. 계정·배포 URL이 없으면 해당 동적 검증만 미실행으로 기록하고 코드 비교는 계속한다.

## A. 자산 및 기능 비교

읽기 범위:
- 현행 `04_봉뜨락_업무로그_AI/` 전체.
- `origin/claude/dreamy-ritchie-jpz4r8`의 `chatlog/`, `netlify-site/`, `seed/`.

경로와 내용 해시를 함께 대조한다. 내용이 다르다는 이유만으로 기능이 없다고 판정하지 않는다. 최소 비교 항목:
- 분류 4종, 담당자·우선순위·마감일 정규화, 빈 입력 및 최대 입력 길이.
- 자동 저장과 수동 승인, 저장 행 수/범위 확인, 실패 표시, 재시도 및 중복 저장 가능성.
- 원장 조회·필터·상태 표기, 연결 진단, 시트 서식 변경, archive 화면의 실제 데이터 출처.
- 접근 코드 적용 범위, AI 제공자/모델 설정의 사용 경로, Apps Script 전용 기능.
- seed 파일 수·형식·용도와 중복 적재 가능성. 실제 seed 데이터를 다시 업로드하지 않는다.

각 항목은 `현행 위치 / 구버전 위치 / 동일·변경·구버전 전용·미확인 / 근거 / 이관 권고`로 정리한다. 테스트 파일도 읽고 실행 가능할 경우 키 없이 실행되는 테스트만 수행한다. 비용 발생 또는 시트 쓰기가 있는 테스트는 아래 환경 조건에 따른다.

## B. 화면으로 연결 상태 확인

접근 가능한 실제 계정 화면에서 다음 연결을 따라간다:

`GitHub 기준 커밋 → Netlify 배포 사이트·배포 커밋 → 업무로그 화면 → 연결된 Google Sheets 탭`

- 배포 화면에서 배포 시각, 성공/실패, 소스 브랜치/커밋, 함수 존재 여부를 확인한다. ZIP 수동 배포라 SHA를 확인할 수 없으면 그 사실을 적는다.
- 현행 master와 배포본이 같은지 구분한다. 다르면 관찰한 버전의 문제로 보고하고 master의 결함으로 단정하지 않는다.
- 사이트 주소는 실제 링크나 관리 화면에서 확인한다. README의 예시 주소를 실제 운영 주소로 가정하지 않는다.
- 환경변수는 이름과 설정 여부만 확인한다. 값이나 키를 펼치거나 보고서에 옮길 필요는 없다.
- 코드에서 부작용이 없음을 확인한 조회·진단만 운영에서 수행한다. 화면의 연결 대상과 실제 탭/헤더를 비교한다.
- 기록 내용·계정 이메일·비밀값은 공개 저장소의 증거 이미지에 담지 않는다. 시트 ID는 보고서에서 식별에 필요한 끝부분만 사용한다.

## C. 사용자 흐름 검증

주의: 현행 화면의 자동 저장 체크는 기본 ON이다. `/api/classify`도 `autosave`가 켜지면 시트에 기록한다. 분류 버튼을 조회용으로 취급하지 않는다. `/api/format` 역시 실제 시트 변경이다.

- 입력·접근 코드·모바일 화면 표시 등 쓰기 없는 동작은 운영 화면에서 확인 가능하다.
- 분류·저장·재시도·서식 변경은 **이미 분리된 테스트 배포와 테스트 시트가 확인된 경우에만**, 해당 환경에서 합성 데이터로 수행한다. 이번 작업을 위해 운영 연결을 테스트 시트로 바꾸지 않는다.
- 테스트 환경이 없다면 로컬 모의 환경으로 검증할 수 있다. 모의 결과는 실서비스 연동 성공으로 보고하지 않는다. LLM 유료 호출이 필요한 부분은 이용 권한과 허용 범위를 확인하고 임의 반복하지 않는다.
- 사례: 정상 분류, 자동 저장 OFF, 수동 전송 1회, 자동 저장 ON, 빈 입력, 잘못된 접근 코드, 새로고침, 같은 입력 재전송/빠른 두 번 클릭. 오류 유발은 테스트 환경에서만 한다.
- 시트 쓰기를 검증할 때는 실행별 고유 표식(예: `GEO-001-날짜-번호`)을 넣고 전후 행 수·표식·반영 범위를 비교한다. 성공 토스트만으로 저장 성공을 판정하지 않는다.
- 재시도는 중복 여부를 확인한 뒤 판단한다. 테스트에서 생긴 행과 남은 상태도 인계한다.

## 완료 기준과 보고

1. 비교한 기준 SHA, 브랜치, 파일 범위가 명확하다.
2. 코드 비교표 및 실제로 확인한 화면/배포/시트 연결 경로가 있다. 미접근·미실행은 이유와 함께 구분한다.
3. 문제마다 재현 단계, 기대/실제 결과, 영향, 근거 위치, 운영/테스트/모의 중 검증 환경을 적는다.
4. 결론을 `유지 / 선택 이관 / 수정 필요 / 추가 확인`으로 나누고, 다음 작업은 3개 이내로 제안한다.
5. 허용 문서와 증거만 커밋·푸시하고 **master 대상 PR을 바로 연다. PR 개설을 다시 허락받을 필요는 없다.** 병합은 벤이 수행한다.
6. 벤에게 PR URL, 커밋 SHA, 핵심 발견 3개, 실행·미실행 검증, 필요한 접근/결정만 전달한다. 지오에게 직접 연결된 벤 채널이 없다면 사용자에게 전달용 보고를 제공한다.
