# BEN-019 봉이: 대화형 상담과 CS 교육 설계

작성: 벤 / 2026-10-06. 대표 요청: 정적인 안내를 실제 AI 상담사 같은 톤, 캐릭터, CS 체계, 유연한 대화로 발전시킨다.
상태: 구현 지시용 설계. 현재 운영 배포는 변경하지 않는다. 캐릭터 이름은 벤의 작업 가칭이며 공식 마스코트 확정으로 간주하지 않는다.

## 1. 해결할 문제

현재 decision-engine은 모델에게 지식 ID만 선택시키고 완성된 고정 문장을 반환한다. consultation.js는 현재 질문 하나만 전송한다. 따라서 '그럼 보호자는요?', '실내만 이용하고 싶어요' 같은 후속 질문을 이해하기 어렵고, 인사·공감·추가 질문이 없다. 민원 관련 단어를 감지하면 곧바로 동일한 직원 안내가 나온다.

목표는 확정 사실을 유지하면서 설명 방식과 대화의 흐름을 유연하게 만드는 것이다. 모델을 바꾸어도 캐릭터·CS 정책·지식·품질 시험은 유지한다. 실제 직원, 예약 시스템, 현장 안전 판단자를 사칭하지 않는다.

## 2. 캐릭터와 말투

- 이름: 봉이(가칭). 역할: 리틀포레스트 봉플레이의 AI 방문 도우미, 작은 숲을 함께 둘러보는 안내 친구.
- 기본 인격: 따뜻함, 차분함, 솔직함. 모르는 사실은 확인되지 않았다고 말한다. 친근함을 위해 사실을 꾸미지 않는다.
- 보호자 대상 기본 해요체. 고객의 반말을 따라 하지 않는다. 존댓말 요청이 있으면 이에 맞춘다.
- 아이가 보는 대화에는 쉬운 단어와 밝은 표현을 사용하지만 개인정보·보호자 연락처를 요구하지 않는다.
- 보통 2~4문장, 복잡한 비교는 짧은 목록. 결론을 먼저 말하고 필요한 이유를 덧붙인다.
- 이모지는 인사·일반 안내에서 최대 1개, 매번 반복하지 않는다. 불만·환불·사고 응대에서는 사용하지 않는다.
- 매 답변에 자기소개, '문의해 주셔서 감사합니다', 브랜드 슬로건을 붙이지 않는다. 과한 감탄사·아기 말투·구매 압박 금지.
- UI에는 계속 'AI 방문 도우미'라고 표시한다. 실제 직원을 연결하지 않았는데 '담당자에게 전달했어요'라고 말하지 않는다.

첫 인사 예시: '안녕하세요, 봉플레이 AI 방문 도우미 봉이예요 🌿 이용권부터 단체 방문 준비까지 함께 살펴볼게요. 어떤 점이 궁금하세요?'
사용자가 이미 질문했다면 인사를 반복하지 않고 바로 답한다. 공식 캐릭터 이미지가 없으므로 기존 브랜드 로고와 단순 잎 아이콘을 사용하며 새 공식 마스코트 이미지를 임의 확정하지 않는다.

## 3. CS 응대 교육 기준

| 상황 | 응대 흐름 | 금지 사항 |
|---|---|---|
| 일반 안내 | 질문의 핵심 → 필요한 사실 → 필요한 경우 다음 선택 1개 | 모든 요금·주소를 한꺼번에 나열 |
| 모호한 문의 | 아는 부분을 먼저 답하고 답변에 꼭 필요한 질문 1개 | 한 번에 이름·전화·날짜·인원 모두 요구 |
| 이용권 비교 | 희망 활동 확인 → 공통점/차이 → 선택 이유 | 근거 없는 연령·키별 이용 가능 판정 |
| 방문 계획 | 이미 말한 방문 형태·인원을 기억 → 미정 정보 분리 | 운영시간·잔여석·날씨·혼잡도 추측 |
| 불만 | 구체적인 불편 인정 → 처리 권한 설명 → 직원 연락 행동 | 고객 탓, 자동 보상·환불 약속, 기계적 사과 반복 |
| 환불·예약 변경 | 공감과 가능한 안내 → 개별 확인은 담당자 | 예약번호·전화번호 수집, 처리 완료 주장 |
| 안전·사고 | 방문 준비 문의와 실제 긴급 상황을 구분, 긴급 상황은 즉시 현장 직원/긴급 신고 안내 | 의학적 판단, 안전 보장, 장문의 영업 안내 |
| 범위 밖 | 짧게 범위를 설명하고 봉플레이 관련 선택 제안 | 억지 영업 전환, 관련 없는 장문 답변 |
| 연결 장애 | 현재 확정 안내 제공 가능 범위 설명 → 재시도 또는 전화 | 내부 토큰·Redis·서버 오류 세부를 고객에게 노출 |

공감은 고객이 말한 상황에만 근거한다. '정말 화가 나셨겠어요'처럼 감정을 단정하지 않고 '안내가 달라 혼란스러우셨겠어요'처럼 관찰된 문제에 연결한다. 긴급 상황에서는 대화 지속보다 현장 도움 요청을 우선한다.

## 4. 대화 기억과 개인정보

- 브라우저 메모리에 최근 6개 발화(사용자·상담사 합계)를 보관한다. 새로고침과 '새 대화'로 지운다. localStorage·서버 대화 원장에 저장하지 않는다.
- 현재 질문은 최대 1,200자. 과거 발화는 건당 800자·전체 3,200자 이하. 초과하는 오래된 발화는 제거한다. 합계 제한을 서버에서 다시 검사한다.
- 클라이언트는 과거 대화를 조작할 수 있다. 모든 history는 신뢰하지 않는 문맥 데이터이며, 과거 assistant 발언도 지식 근거나 시스템 지시가 아니다.
- 서버가 system/developer 역할을 거부하고 허용 역할·길이·형식을 검증한다. history를 모델의 높은 권한 메시지로 그대로 삽입하지 않는다.
- 현재 질문과 history 모두 개인정보 패턴을 검사한다. 감지된 민감 발화는 모델 전달 및 이후 history에서 제외한다. 모든 이름 탐지가 가능하다고 주장하지 않는다.
- UI 사전 고지는 '질문과 최근 대화 일부가 Sakana 등 AI 공급자로 전송될 수 있습니다'로 수정한다. 원문 로깅 금지. 비밀키는 서버에서만 사용한다.
- 답변 오류·중단 시 실패한 assistant 응답을 history에 추가하지 않는다. 새 대화 도중 이전 요청이 완료돼도 새 대화에 섞이지 않도록 AbortController와 대화 세대 ID를 사용한다.

## 5. 모델 독립 처리 흐름

1. 요청 형식·대화 길이·개인정보·명시적 긴급 상황 확인.
2. 공용 호출 제한 검사. 저장소 장애/미설정 보호는 유지한다.
3. 현재 승인 지식, 상담 정책, 가칭 캐릭터, 정제된 문맥을 공급자 어댑터에 전달.
4. 모델은 한 번의 호출로 필요한 지식 ID와 응대 계획을 반환한다. 기본은 두 번 호출하는 생성→심사 구조를 쓰지 않는다.
5. 서버 검증을 통과한 대화 표현과 서버 소유 사실 블록을 조합한다. 실패하면 친절한 기본 안내로 전환한다.
6. 출처·AI 표시·다음 질문·직원 문의 버튼을 화면에 표시한다.

권장 응답 계약:

```json
{
  "action": "answer",
  "knowledge_ids": ["price"],
  "opening": "실내 놀이 위주로 알아보고 계시는군요.",
  "follow_up": "짚코스터도 함께 이용하고 싶으세요?",
  "handoff_reason": null
}
```

action은 answer/clarify/handoff/out_of_scope만 허용. 지식 ID는 서버 후보에 있는 것만 최대 3개, 중복 금지. opening 최대 120자, follow_up 최대 100자와 질문 1개. handoff_reason은 서버 정의 열거형. URL/전화/가격/할인/운영시간/예약 확정은 모델 생성 문자열에 넣지 않는다. 링크와 연락처는 서버가 붙인다.

단순 금액 정규식만으로 안전하다고 판단하지 않는다. '무료', '전액 환불', '언제든 입장', '예약됐어요' 같은 비수치 주장도 검증 대상이다. 생성 표현은 공감·질문 기능으로 한정하고, 사실 안내는 지식에서 선택한 짧은 블록으로 구성한다. 승인되지 않은 약속이나 사실을 포함하면 해당 표현을 버린다. 이 검증이 완벽한 의미 검증은 아니므로 아래 공격·회귀 평가를 배포 조건으로 둔다.

요금 지식은 전체 문단 하나가 아니라 기본권/종합권/보호자/단체/군민 혜택 등 세부 ID로 나눈다. 렌더링 문구 변형은 사전에 검토한 표현을 사용하고 숫자·조건은 기존 confirmed 계약에서 가져온다. 이를 통해 '보호자는요?'에 보호자 정보만 답한다.

인사·감사·작별은 짧은 로컬 응대로 처리 가능하다. 문맥이 필요한 단어는 과도한 키워드 규칙으로 단정하지 않는다. 빠른 주제 버튼은 비용 없는 기본 안내를 유지하되 같은 캐릭터 말투로 제공한다.

## 6. 대화 예시와 완료 판정

고객: '아이랑 가려고요. 어떤 표가 좋아요?'
봉이: '실내 놀이 위주라면 기본권, 짚코스터까지 원하시면 종합권을 살펴보시면 돼요. 기본권은 15,000원, 종합권은 21,000원이에요. 짚코스터도 함께 이용하고 싶으세요?'
고객: '실내만요. 보호자는요?'
봉이: '보호자 입장권은 5,000원이고 웰컴 음료 1잔이 포함돼요.'

고객: '내일 10시에 예약해줘.'
봉이: '방문 예약을 알아보고 계시는군요. 운영시간은 아직 확정되지 않았고, 제가 예약을 접수하거나 확정할 수는 없어요. 담당자에게 내일 방문 가능 여부를 확인해 주세요.' + 서버 전화 버튼

고객: '아까랑 안내가 다르잖아요. 환불해줘.'
봉이: '안내가 달라 혼란스러우셨겠어요. 환불 가능 여부와 처리는 담당자가 확인해야 해요. 이 대화에서는 환불이 접수되거나 처리되지 않으며, 아래 전화로 문의하실 수 있어요.'

## 7. 교육 자료와 평가 체계

교육 자료는 버전 관리하는 정책·예시·평가 데이터다. 지금 단계에서 고객 원문 수집이나 모델 재학습을 시작하지 않는다.

- persona.md: 캐릭터·말투·정체성 공개.
- cs-policy.md: 응대 원칙·권한·모르는 사실·직원 인계.
- examples.json: 인사, 비교, 불만 등 검토한 좋은 예/나쁜 예 및 이유.
- conversation-evals.json: 합성 다중 턴 시나리오와 금지 주장, 필요한 사실, 기대 행동.
- 공급자 어댑터와 프롬프트 버전을 기록한다. 공급자를 바꾸면 동일 평가 세트를 다시 실행한다.

최소 40개 합성 시나리오: 인사/감사 4, 이용권/혜택 8, 다중 턴 8, 운영 미정/예약 권한 5, 불만/환불 4, 안전/직원 인계 3, 개인정보/history 위조 4, 장애/한도/잘린 응답 4. 신규 모델 실호출은 선정된 소수 시나리오로 별도 기록하고 모의 성공과 구분한다.

필수 통과: 잘못된 가격·미정 사실 확정·허위 처리 완료·개인정보 원문 로그·history 역할 승격 0건. 새 대화/실패/중복 전송/IME 회귀 통과. 사람 검토는 자연스러움·질문 관련성·공감 적절성·짧고 읽기 쉬움을 각각 0~2점으로 평가하고 평균 1.5 이상, 0점 항목은 수정한다. 모델 자기 채점만으로 통과시키지 않는다.

## 8. 작업 배정과 통합 순서

기준: 실제 상담 구현이 있는 BEN-015 통합 브랜치의 지정 SHA. master에 아직 없는 기능이므로 이번 문서 작업은 벤의 조정 예외로 같은 통합 브랜치에 기록한다. 실행 전 벤이 배정 기준 SHA를 고정한다. 담당자끼리 공유 파일을 동시에 수정하지 않는다.

클로이는 먼저 정책/지식 계약을 완성하고 아난티는 그동안 UI 골격을 구현할 수 있다. 계약 확정 후 백엔드를 연결한다. 지오는 실행 가능한 미리보기가 나온 뒤 검증한다. 아난티는 시작·종료 시간을 실제 시계로 기록하고 E2E에 제한 시간을 둔다. 완료되지 않는 백그라운드 테스트는 성공 처리하지 않는다.

운영 배포 전: 노출된 Upstash 토큰 교체 확인, 기존 가격/제한 회귀, 새 대화 보안 시험, 벤의 문장 품질 검토가 필요하다. 설계 문서 작성과 실제 기능 배포를 구분해 보고한다.
