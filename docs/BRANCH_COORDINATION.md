## 파일 이관 시 주의점

- `agents/`: master에 없는 Python 에이전트 코드와 테스트. 실행 요건과 사업 기준값 검토 후 새 위치 결정.
- `chatlog/`: master에 없는 Google Apps Script 구현. 현행 Netlify 업무로그와 병행할지 결정 필요.
- `netlify-site/`: master의 `04_봉뜨락_업무로그_AI/`와 대응. API 파일은 master 쪽에 394줄이 추가된 것으로 비교되므로 과거 파일로 덮어쓰지 않는다. 화면·설정도 별도 비교한다.
- `seed/`: 업무로그 초기 자료. 실제 운영 데이터의 재적재·중복 저장을 방지하며 필요 여부부터 검토한다.
- JEV 분석, 지식 시스템 설계, 운영계획과 제안서: 현재 운영 기준과 날짜를 대조한 뒤 문서 위치를 정한다.

## 통합 순서

1. 완료: 원격 fetch, 브랜치 계보 확인, 열린 PR 조회, 전체 Git bundle 백업과 검증.
2. 로컬 준비: `ben/repository-coordination`에서 공동 규칙과 이 문서를 작성.
3. 완료: GitHub 기본 브랜치를 `master`로 전환. 별도 배포 서비스와 각 에이전트의 기준 브랜치 설정은 담당 확인 필요.
4. 공동 규칙을 새 브랜치로 푸시하고 `master` 대상 PR로 검토·반영.
5. 구 브랜치의 고유 자산을 목적별 작업으로 나누어 이관. 통합 전후 파일과 필요한 테스트를 비교.
6. 각 담당의 미푸시·진행 중 작업이 없는지 확인한 뒤 보존 태그를 원격에 검증하고, 불필요한 브랜치를 정리.

기본 브랜치 설정 변경만으로 파일이나 배포 대상 코드가 통합되는 것은 아니다. 기본 브랜치 전환은 완료했으며, 기존 브랜치의 코드 이관과 삭제는 후속 작업이다.
