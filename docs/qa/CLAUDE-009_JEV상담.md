## 1. 구조

- `knowledge.mjs` 의 `facts` 에 고객 답변에 쓰는 사실값을 모았다. 각 값에는 다음을 둔다.
  - 상태
  - 표시값
  - 근거: 출처 키와 항목
  - 홈페이지 대조 기준
  - 05 대조 기준
- `SOURCES` 에는 출처 파일 9개의 경로, blob SHA, 마지막 변경 commit 을 기록했다. 모두 기준 커밋에서 `git rev-parse 934dd0f:<path>` 와 `git log -1 -- <path>` 로 계산한 값이다. 추측한 SHA 는 없다. 시험이 현재 파일 바이트로 git blob 해시를 다시 계산해 기록값과 대조한다.
- 상태 5종과 고객 안내 가능 여부

  | 상태 | 뜻 | 안내 |
  |---|---|---|
  | `confirmed` | 대표 결정 또는 05 confirmed 근거 있음 | 안내 가능 |
  | `published` | 홈페이지 고지만 있음 | 기준정보는 안내 금지 (연락 채널만 예외) |
  | `undetermined` | 대표가 미정으로 결정 | 값 금지, "확정 후 안내" |
  | `planned` | 계획 단계 | 값 금지 |
  | `abolished` | 대표가 폐지 결정 | 어떤 출력에도 나오면 안 됨 |

  근거는 BEN-004 의 "오래된 confirmed와 새 근거가 충돌하면 해당 값은 고객용 출력에서 보류" 이다.
- `renderAnswers(facts)`: 사실값으로 고정 답변을 만든다. 안내할 수 없는 값은 값 없이 문의 안내로 바꾼다. 상태가 바뀌면 답변이 자동으로 따라간다.
- `checkKnowledge({homepage, siteProfile, blobs, notices})`: 원문을 넘겨받아 사실별로 `ok`(정상), `missing`(누락), `mismatch`(불일치), `uncertain`(불확실) 을 분류한다. 파일을 읽지 않고 네트워크도 쓰지 않는다.
- `consultation.mjs`: `answers` 와 `contact` 를 계약에서 받도록 바꿨다. `consult` 의 입력·출력 계약은 그대로다: 출력 키 7개와 순서, `source` 문자열, `contact` 값, 오류 처리, JEV 분류 경로.
