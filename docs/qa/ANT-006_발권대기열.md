## 1. 개요 및 목적

본 과업은 리틀포레스트 봉플레이 운영 시스템(`01_봉플레이_운영시스템/`)에서 현장 혼잡 방지 및 고객 편의 증대를 위한 **발권 대기열 시스템 (Ticketing Queue System)** 을 완결하는 작업이다.

### 핵심 업무 흐름
```
[고객 모바일] QR 동의서(안전서약) 서버 접수
       ↓ (원자적 공식 대기번호 채번)
[고객 모바일] 팀별 대기번호 & 실시간 대기 순서·예상시간 확인 (내 대기 화면)
       ↓ (실시간 호출 전파 / 음향·진동 알림)
[매표소 데스크] 창구별 다음 고객 호출 및 접수 확인 (다중 창구 경합 방지)
       ↓ (결제·원장 대사 및 팔찌 발권)
[서버 확정] 발권 완료 즉시 대기열에서 완전 제외 (통계 처리시간 갱신)
```

- **1 동의서 = 1팀(일행)** 원칙 적용 (개인별 대기열이 아님).
- **놀이시설(짚코스터 등) 탑승 대기는 범위 외**이며, 순수 매표·발권 대기에 집중.
- 운영 DB 무단 적용 및 Netlify 실배포를 엄격히 금지하고, 로컬 합성 환경 및 실제 헤드리스 브라우저 세션(CDP)을 통해 시간 제한 기반의 전수 E2E 검증을 완결함.

## 2. 핵심 동작 원칙 및 불변식 (Invariants) 준수

### 2.1 벤(Ben) R1 검토 6대 필수 수정사항 반영 상세
1. **[Fix 1] 서버 실패 시 로컬 가짜 번호 채번 폴백 원천 차단**: 서버 에러 시 로컬 저장소로 임의 채번하던 동작 제거, `normalizeRpcResult`로 전송 및 본문 검증 후 에러 반환.
2. **[Fix 2] 직원 인증 및 128비트 `customer_token` 보안 분리**: RLS 격리, 128비트 암호화 토큰 도입, 공개 전광판 Zero PII 엄수.
3. **[Fix 3] 서버 발권 완료 증명 및 원장 반영 보장**: `order_id` 및 `ticket_ids` 무결성 검증, 결제 완료 시 티켓 원장 비동기 저장 완결 대기.
4. **[Fix 4] 멱등키 선점 및 단일 창구 1팀 제약**: `pg_advisory_xact_lock` 선점, 동일 멱등키 타 서약서 재사용 차단, 발권 완료 건 취소 불가 가드.
5. **[Fix 5] 부재 복귀 순서 규칙 (Back of the Line)**: `order_key = MAX(order_key) + 1` 맨 뒤 재배치로 새치기 차단.
6. **[Fix 6] 서버 상태 일원화 및 예상시간 범위 산출**: 서버 RPC 및 `ticket_queue_desks` 일원화, 20초 미만/1800초 초과 이상치 필터링, 사분위수(P25~P75) 범위형 추정치 제공.

### 2.3 벤(Ben) 지시 및 PR #35(c17318e, §10) 기준 R3 필수 수정사항 반영 상세

| 항목 | R3 필수 수정 요구사항 | 구현 내용 및 기술적 무결성 보장 |
|---|---|---|
| **R3 Fix 1** | **다른 팀 주문 연결 차단 (Reject another team's order)** | `complete_queue_issuance`에서 `order_payments` 및 `ticket_ledger`의 `consent_id`가 대기열 행의 `v_rec.consent_id`와 일치하는지 강제 대사. 타 서약서 소속 주문(`ord_B`)이나 티켓(`T_B1`)이 전달될 경우 `ORDER_CONSENT_MISMATCH` 및 `TICKET_CONSENT_MISMATCH`로 즉시 거부 (회귀 결함 원천 해결). |
| **R3 Fix 2** | **주문 수량 대비 티켓 수 대사 (Order quantity vs ticket count)** | `public.order_items`의 주문 수량(`SUM(quantity)`)을 집계하여, 발권 요청된 티켓 수(`cardinality(p_ticket_ids)`)가 주문 수량보다 적을 경우 `TICKET_QUANTITY_MISMATCH` 에러로 발권 거부. |
| **R3 Fix 3** | **결제 총액 대비 수납 합계 대사 및 부분 수납 거부 (Payment sum verification)** | `public.order_items`의 주문 총액(`SUM(total_price)`)과 `public.order_payments`의 유효 수납 합계(`SUM(amount) WHERE status = 'paid' AND cancelled_at IS NULL`)를 대사하여, 수납 합계가 주문 총액에 미달할 경우 `PARTIAL_PAYMENT_REJECTED` 에러로 발권 거부. |
| **R3 Fix 4** | **`processing` 상태 강제 (Completion from called rejected)** | 계약 §2.1에 따라 호출(`called`) 상태에서의 완료 시도를 원천 차단(`INVALID_STATUS`). 직원이 창구에서 실물 처리를 개시한 `processing` 상태의 대기팀만 발권 완료를 허용. |
| **R3 Fix 5** | **암호화 함수 경로 보완 (Crypto function search_path)** | Supabase 표준 레이아웃(`supabaseExtensions: true`, `FINAL_SUPABASE_SETUP.sql`)에서 `pgcrypto`가 `extensions` 스키마에 상주하므로, `enqueue_consent_team`을 비롯한 마이그레이션 내 전체 RPC에 `SET search_path = public, extensions, pg_temp;`를 적용하여 비한정 `gen_random_bytes` 호출 실패(Postgres 42883) 해결. |
| **R3 Fix 6** | **원장 테이블 부재 시 실패 강제 (Fail if ledger tables missing)** | `order_payments`, `ticket_ledger`, `order_items`, `safety_consents` 4대 원장 테이블의 존재 여부를 검증하고, 테이블이 누락된 경우 조용히 발권을 통과시키지 않고 즉시 `LEDGER_TABLE_MISSING` 실패를 반환. |

## 5. 공통 인증 및 동기화(Sync) 아키텍처 연계안 (벤 분리 보고)

### 5.1 현행 구조와 도전 과제
- 웹 프런트엔드 애플리케이션(`bongplay-sync.js`)은 브라우저에서 `SUPABASE_ANON_KEY`를 통해 PostgREST 및 RPC를 호출합니다.
- 이에 따라 PostgreSQL 내부의 `auth.role()`은 일괄 `'anon'`으로 평가됩니다.
- 만약 DB 수준에서 RLS 정책이나 함수 실행 권한을 `TO authenticated`로만 일괄 한정하면, 직원이 브라우저에서 매표소 화면을 사용할 때 모든 조작이 `403 Permission Denied`로 거부되는 문제가 발생합니다.
- 반대로 `'anon'` 호출을 무제한 허용하면, 외부 악의적 사용자가 public anon key를 획득하여 직원용 RPC(`call_next_queue_team`, `complete_queue_issuance` 등)를 임의 호출할 위험이 있습니다.

### 5.2 ANT-006 채택 해결책 (공용 키 전송 안전 연동)
- **RPC 파라미터 수준의 서버 검증 (`p_access_code`)**:
  - 클라이언트(`bongplay-queue.js`)는 직원 조작 시 `window.BongplayAuth.getAccessCode()`로부터 획득한 암호화 인증 코드를 `p_access_code` 인자로 동봉합니다.
  - PostgreSQL 제안 함수(`PROPOSED_MIGRATION_ticket_queue.sql`)는 내부에서 `private.verify_staff_permission(p_access_code, p_site_id)`을 호출합니다.
  - `private.verify_staff_permission`은 기존 `private.verify_access_code`를 활용하여 bcrypt 해시 대조, 실패 횟수 제한(Rate Limit), 시설 화이트리스트(`bongplay_bonghwa` 등)를 검증합니다.
  - 검증 실패 시 즉시 `RAISE EXCEPTION 'UNAUTHORIZED_STAFF'` 또는 `INVALID_SITE`로 차단합니다.
  - 프런트엔드가 전달하는 `p_staff_id`(직원 성명/ID)는 단순 감사 로깅용 문자열일 뿐이며, 권한 판정의 근거로 일절 사용되지 않습니다.

### 5.3 향후 전사 아키텍처 개선 제안 (벤 검토 요청)
- 현재 방식은 공용 anon key 환경에서도 완벽한 서버 측 보안을 보장하지만, 장기적으로 전사 시스템의 보안 수준을 높이기 위해 다음 2가지 방향을 벤에게 건의합니다:
  - **옵션 A (Supabase Auth 통합)**: 매표소 직원 로그인 시 `supabase.auth.signInWithPassword()`를 통해 실제 직원 세션 JWT를 발급받고, Postgres RLS에서 `auth.jwt() -> 'role' = 'staff'`를 평가하는 방식.
  - **옵션 B (서명된 HMAC 직원 세션 토큰)**: 별도 Edge Function 또는 백엔드 인증 게이트웨이에서 서명된 단기 직원 토큰을 발급받아 RPC 헤더/인자로 전송하는 방식.
- 본 ANT-006 작업에서는 회계나 공통 모듈에 영향을 주지 않기 위해 독자적인 침해 없이 `p_access_code` 검증 경로를 완성하였습니다.
