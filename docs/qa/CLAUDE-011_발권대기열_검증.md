## 2. 시나리오와 계약 조항

| 시나리오 | 확인하는 계약 |
|---|---|
| S1 번호·접수 멱등성 | §3 번호 1부터, §4 재시도·응답 유실·새로고침은 같은 결과, 키 재사용 거부, **같은 전화번호 차단 안 함**, 같은 번호 활성 수는 표시만 |
| S2 앞선 팀 수·부재 복귀 | §3 `waiting/called/serving` 포함, `issued/held` 제외. §6 복귀하면 번호 유지·맨 뒤 합류·감사 기록(이전·새 order_key) |
| S3 복수 창구 경합 | §9.2 같은 팀이 두 창구에 호출되지 않음, `COUNTER_BUSY`, `VERSION_CONFLICT`, 같은 `request_id` 재요청은 처음 결과, `COUNTER_NOT_OPEN` |
| S4 원장 확정·재시도 | §7 원장 없음·티켓 일부 누락·결제 부족·다른 동의서 주문은 `LEDGER_NOT_CONFIRMED` 이고 `serving` 유지. 같은 `request_id` 재시도로 완료. 완료 뒤 중복 완료 거부. **발권 취소 후 자동 복귀 없음** |
| S5 취소·잘못된 전이 | §2.1 종료 상태에서 전이 불가, `serving` 취소는 사유 필수, 발권 완료는 `issueComplete` 로만 |
| S6 권한·개인정보 | §9.1·§11 직원 코드 불일치는 `UNAUTHORIZED`, 추측 토큰은 `TOKEN_INVALID`. 고객·호출판 응답 키 제한. 이름·전화·자녀·서명·동의서 id 비노출 |
| S7 영업일 종료 | §8 비종료 항목 `closed`, 종료 뒤 같은 날 접수 거부, 다음 영업일 1번부터, 지난 토큰 만료 |
| S8 KST 영업일 경계 | §3 23:59:59 KST 와 00:00:00 KST(=15:00Z)가 다른 영업일. UTC 날짜로 번호를 매기면 실패하도록 설계 |

## 5. 시험을 쓰며 발견한 계약 보완점 (v1.1 제안 — 벤 검토 후 반영)

v1 은 벤 검토 중이므로 계약 문서를 고치지 않고 여기 기록한다.

1. **"0~0분" 표시**: 앞 팀이 없고 창구가 비어 있으면 `max_minutes = 0` 이 된다. 고객 문구를 "곧 호출 예정" 으로 정하는 것을 제안한다 (§10.3 표에 추가).
2. **정지된 창구에 남은 `called/serving`**: 창구를 정지해도 그 창구의 호출·처리 중 팀은 앞선 팀 수에 포함된다. 그런데 처리할 창구가 없다. 참조 모델은 이 팀을 대기 팀으로 보고 예상시간에 넣는다. 계약에 명시할 것을 제안한다. 직원이 창구를 정지할 때 해당 팀을 보류·이관하도록 안내하는 것도 대안이다.
3. **`serving` → `held` 의 원장 조건**: 계약은 "원장 미확정일 때만" 이라고 썼다. 참조 모델은 원장 상태를 전이 시점에 검사하지 않는다. 구현에서는 원장이 확정된 주문이 있으면 `held` 대신 `issueComplete` 를 유도해야 한다. 이를 확인하는 시험은 구현 어댑터가 원장 조회를 제공할 때 추가한다.
4. **`queue_staff_list` 의 `position`**: 계약 표에는 있지만 정의가 없다. "활성(`waiting/called/serving`) 항목 중 `order_key` 순위" 로 정의할 것을 제안한다.
5. **토큰 만료 시각**: 영업일 종료 시점을 참조 모델은 `YYYY-MM-DDT23:59:59+09:00` 으로 표기한다. [결정 요청 C1] 의 영업일 경계가 정해지면 함께 확정한다.

## 6. 미실행

- 실제 구현과의 대조: 아난티 구현이 아직 없다. 구현 인계 후 어댑터로 실행한다.
- Supabase 실제 동시성 (`for update skip locked`, 트랜잭션 격리): 참조 모델은 단일 스레드라 경합을 순차 호출로만 재현한다. 실제 DB 동시 호출 시험은 구현 대조 단계에서 한다.
- 요청 제한(`RATE_LIMITED`)과 HMAC 토큰 생성: 참조 모델 범위 밖이다. 구현 대조 때 확인한다.
- 화면(고객·직원·호출판)의 오래된 정보 표시: 화면 구현 이후 확인한다.
- 운영 DB 적용, 배포, 실제 접수, 결제
