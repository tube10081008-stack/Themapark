## 5. 시험을 쓰며 발견한 계약 보완점 (v1.1 제안 — 벤 검토 후 반영)

v1 은 벤 검토 중이므로 계약 문서를 고치지 않고 여기 기록한다.

1. **"0~0분" 표시**: 앞 팀이 없고 창구가 비어 있으면 `max_minutes = 0` 이 된다. 고객 문구를 "곧 호출 예정" 으로 정하는 것을 제안한다 (§10.3 표에 추가).
2. **정지된 창구에 남은 `called/serving`**: 창구를 정지해도 그 창구의 호출·처리 중 팀은 앞선 팀 수에 포함된다. 그런데 처리할 창구가 없다. 참조 모델은 이 팀을 대기 팀으로 보고 예상시간에 넣는다. 계약에 명시할 것을 제안한다. 직원이 창구를 정지할 때 해당 팀을 보류·이관하도록 안내하는 것도 대안이다.
3. **`serving` → `held` 의 원장 조건**: 계약은 "원장 미확정일 때만" 이라고 썼다. 참조 모델은 원장 상태를 전이 시점에 검사하지 않는다. 구현에서는 원장이 확정된 주문이 있으면 `held` 대신 `issueComplete` 를 유도해야 한다. 이를 확인하는 시험은 구현 어댑터가 원장 조회를 제공할 때 추가한다.
4. **`queue_staff_list` 의 `position`**: 계약 표에는 있지만 정의가 없다. "활성(`waiting/called/serving`) 항목 중 `order_key` 순위" 로 정의할 것을 제안한다.
5. **토큰 만료 시각**: 영업일 종료 시점을 참조 모델은 `YYYY-MM-DDT23:59:59+09:00` 으로 표기한다. [결정 요청 C1] 의 영업일 경계가 정해지면 함께 확정한다.

- 실제 구현과의 대조: 아난티 구현이 아직 없다. 구현 인계 후 어댑터로 실행한다.

### 8.5 적합 확인

- KST 영업일 계산은 정확하다 (`TIMEZONE('Asia/Seoul', NOW())::DATE`).
- 일별 채번은 advisory lock 안에서 한다.
- 다음 팀 선택에 `FOR UPDATE SKIP LOCKED` 를 쓴다.
- 앞선 팀 수 집계 대상 상태(waiting/called/processing)는 계약과 같다. 단 순서 키 문제는 D5 다.
- 오프라인 감지 시 번호를 주지 않는다 (`navigator.onLine` 거짓일 때). 다만 온라인 실패 경로는 D3 이다.
- 고객 상태 응답에 이름·전화가 없다.
- 표본 부족 시 "집계 중" 을 표시하고, 표본 범위 20~1800초를 거른다.
- ANT-006 자체 시험 10/10 통과.
