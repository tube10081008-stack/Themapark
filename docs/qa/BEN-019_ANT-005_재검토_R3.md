## 벤의 구현 결정: 금칙어 추가 반복을 끝내고 출력 구조로 제한

이번 릴리스에서는 모델 생성 opening/follow_up 원문을 고객에게 직접 붙이지 않는다. 모델은 대화 문맥을 해석해 다음을 선택한다.

1. action 및 knowledge_ids: 지금과 동일하게 승인 지식만 선택.
2. opening_id: 서버가 관리하는 공감/도입 표현 중 하나 또는 none.
3. follow_up_id: 서버가 관리하는 후속 질문 중 하나 또는 none.
4. handoff_reason: 기존 열거형 유지.

모델은 여전히 자유 질문·지시어·정정·다중 의도를 해석한다. 문장 조합과 후속 질문을 상황에 맞게 선택하므로 모든 문의를 같은 고정 문단으로 답하지 않는다. 새로운 공감 표현이나 지식의 재표현은 검토 가능한 문구 카탈로그로 추가한다. 실시간 모델 원문의 사실 주장을 정규식만으로 안전하다고 보장하지 않는다.

응답 계약은 v2로 올리고 구 v1의 opening/follow_up 원문은 운영 경로에서 거부 또는 폐기한다. 기존 HTTP 응답의 answer/follow_up은 서버가 승인 문구를 렌더링한 결과로 유지해 UI와 QA 도구의 호환을 보존한다. 변경 필드는 내부 모델 계약에 한정한다.

카탈로그 기준:
- 도입: none, general_help, visit_planning, acknowledged_correction, refund_inquiry, reported_discrepancy 등 8~12개.
- 질문: none, choose_topic, desired_activity, group_size, clarify_question 등. 이름·전화·예약번호를 요구하는 문구 금지.
- 모든 표현에 허용 action/상황 태그를 지정한다. 환불에 활기찬 이모지, 단순 질문에 사과처럼 부적절한 조합을 걸러낸다.
- 이미 제시된 인원을 다시 묻지 않고, 정보가 충분하면 follow_up_id=none. 확인되지 않은 고객 사정은 도입 문장에 단정하지 않는다.
- 숫자·금액·주소·운영시간은 지식 블록에서만 렌더링. 고객 원문이나 모델 자유 문자열을 템플릿 슬롯에 넣지 않는다.

## 아난티 후속 범위
conversation-engine 및 해당 시험만 먼저 수정. 모델 스키마·서버 검증·렌더러의 3곳을 일치시키고 알 수 없는 ID/추가 자유 문자열/문맥과 맞지 않는 선택을 거부한다. approved 문구 데이터는 버전 관리하고 ZIP 허용 목록도 확인한다. 현재 UI/지식 계약의 완료된 수정은 유지한다.
