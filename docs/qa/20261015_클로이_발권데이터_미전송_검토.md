## 0. 결론 (요약)

1. **주원인 (재현됨)**: 매표 화면은 발권 완료 뒤 서약서를 저장할 때 `status`·`cancelled_at`·`cancel_reason` 을 함께 보낸다.
   - DB 계약(FINAL + e8a9041)의 `safety_consents` 에는 이 열들이 없다 → PostgREST `400 PGRST204`.
   - `bongplay-sync.js` 는 이 열들을 "중요 열"로 보고 outbox 에 **영구 보류**(`schema_blocked`)한다.
   - 화면은 "✅ 발권 완료"와 "네트워크 복구 시 자동 동기화"를 띄운다. 그러나 서버의 서약서는 계속 **미발권**이고 자동 동기화도 되지 않는다.
   - 주문·결제·티켓·대기열 완료는 저장된다.
   - 열을 더하는 기존 제안 SQL(`PROPOSED_MIGRATION_safety_consents_cancellation.sql`) 하나만 추가하면 해소됨을 확인했다 (E0·E7).
   - e8a9041 설치 묶음이 이 파일을 "화면이 쓰지 않음"으로 판단해 뺀 것은 **제 판단 오류**였다.
2. **안전점검 게이트 불일치 (재현됨)**: 화면은 단말 `localStorage` 의 점검 기록으로 게이트를 열고, 서버 트리거는 서버 `safety_audits` 를 본다.
   - 서버에 오늘 PASS 가 없으면 주문·결제·티켓 쓰기 6건이 전부 `SAFETY_INTERLOCK_BLOCKED` 로 거부되어 outbox 에만 남는다 (E1).
3. **중복 매출 (재현됨)**: 부분 실패 뒤 직원이 결제 창을 닫았다 다시 열고 결제하면 새 주문이 만들어진다.
   - 결과: **주문 2건·결제 합계 40,000원(실제 판매 20,000원)**.
   - 대기열은 그중 하나에만 연결되고, 다른 하나는 결제 `paid` 로 남는다 (E5).
4. **직원 암호 잠금 공유 (재현됨)**: 같은 공인 IP 뒤 단말 하나가 틀린(옛) 암호로 20회 호출하면, 올바른 암호를 쓰는 매표 단말의 발권 완료도 `UNAUTHORIZED_STAFF` 로 거부된다. 결과적으로 대기열이 `processing` 에 머문다 (E6).
5. **정상 동작 확인**: 같은 결제 창 안의 재시도는 계약대로 동작한다.
   - 원장 일부 실패 후 재시도(E2), 완료 응답 유실 후 재시도(E3), 주문 품목 저장 응답 유실(E4) 모두 주문 1건·결제 1건·대기열 완료.

시험 없이 코드로만 확인한 것 (재현하지 않음):
- **S1** FINAL 의 `audits_update` 정책이 `current_date`(UTC)로 비교한다. KST 00~09시에는 오늘 점검 기록의 수정(PATCH·병합 저장)이 거부된다.
  - 서약서 정책은 같은 문제를 KST 로 이미 고쳤다.
  - 현재 점검 화면은 저장마다 새 id(`LOG_<시각>`)로 INSERT 하므로, 지금 경로에서는 영향이 작다.
- **S2** `bongplay-sync.js` 는 `schema_blocked` 를 `queued: true` 로 돌려준다. 화면은 이를 "자동 동기화됩니다"로 안내하지만, 열이 생기기 전에는 절대 성공하지 않는다.
- **S3** 서약서 저장 1건이 카멜 표기 열 10개를 하나씩 지우며 **HTTP 11회**를 쓴다 (마이그레이션 적용 후 E7 관찰). 지운 열 목록은 세션 동안 기억된다.
